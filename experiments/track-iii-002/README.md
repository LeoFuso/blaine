# Track III.2 — Deterministic hierarchical context semantics

**PASS — isolated executable specification, 2026-09-23.**

Hypothesis: a generic ContextNode tree plus a trusted current-context binding can
enforce downward permitted inheritance and current-context writes deterministically,
without special memory classes or any model/backend/runtime integration.

The [III.1 report](../../docs/research/track-iii/001-reference-systems.md) supplies
the accepted principles. The user's III.2 assignment supersedes III.1's suggested
fixture topology with the exact 11-context tree below and explicitly permits
deferring cache tests when no cache exists. III.1 was not repeated. Its artifacts
were preserved in local baseline commit `3960289` before this increment.

## Boundary and implementation

[evaluator.py](evaluator.py) is a Python standard-library experiment. It defines
immutable `ContextNode` and `ScopedEntry` values, an opaque `BoundContext`, and
`ContextTree`. These names are not an adopted production API. There are no runtime
imports, network calls, model calls, persistent stores, queues, timers or services.

The trusted harness constructs and validates the whole tree and calls `bind()`.
An issued binding is registered by object identity in that tree. The caller-facing
`handle(binding, request)` accepts only:

```json
{"op": "read"}
{"op": "get", "entry_id": "root-memory"}
{"op": "write", "entry_id": "new-observation", "content": "literal text"}
```

The request cannot choose a context, ancestor list, scope, destination or policy.
Additional fields and unknown operations are rejected before mutation. New writes
derive their owner exclusively from the issued binding. A token constructed by a
caller, a context-ID string, or a token from another tree is rejected. `bind()`
is trusted fixture setup, not an operation exposed through the request language.
This is an application-boundary model, not a sandbox against Python code with
access to the tree object, its internals or its trusted construction methods.

Each non-root node has one parent; the sole root has none. Constructor validation
rejects malformed topology before an object is returned, even if the defect lies
beyond a closed read boundary. Kind strings never participate in evaluation.
The optional-policy concept is modeled with a **required boolean fixture field**
`inherit_parent`: false ends ancestor reads at that node. This deliberately small
trusted fixture switch is not PolicyGate, security-domain policy or declassification.
Missing/nonboolean values reject construction. All switches in the canonical tree
are true. Entries are owned by valid contexts, uniquely identified, and immutable;
the store is append-only for the experiment. Results sort by entry ID, not relevance.

`visible(C)` contains C's entries and each ancestor's entries until a trusted closed
inheritance edge or root. The caller never supplies that lineage. `get(id)` uses
the same resolved set; knowing an ID supplies no read authority. An unknown and an
invisible ID receive the same `not_visible` result. Diagnostic storage snapshots
in the test harness are not part of the caller interface.

## Exact fixture and independent oracles

```text
root
├── personal
│   └── project-a
│       ├── task-a1
│       │   └── work-a1
│       └── task-a2
└── employer-x
    └── project-x
        ├── task-x1
        │   └── work-x1
        └── task-x2
```

[fixtures.json](fixtures.json) contains every node, one distinct literal entry per
node (`<context-id>-memory`), **hand-specified expected visibility sets**, write
observers, forged requests, malformed inputs and additional boundary/extension
cases. Expected lineage is not generated by the evaluator. There is no similarity
search or semantic ranking. The full fixture and actual/expected values are machine
readable without relying on this prose.

## Results

All **221 cases pass**, across the following invariant groups:

| Group | Cases | What the exact oracle demonstrates |
| --- | ---: | --- |
| Exact lineage visibility | 11 | Every context's exact set; root only itself; work-a1 inherits work-a1/task-a1/project-a/personal/root; parent, sibling, cousin, unrelated and deep-descendant exclusions. |
| Direct-ID isolation | 122 | All 11 × 11 context/entry pairs, checking full returned records or exact denial; plus an unknown ID. Includes task-a1 attempting work-a1, task-a2, project-x and task-x1. |
| Binding authority | 18 | Seven forged read parameters, five destination-write attempts, no mutation, constructed/foreign/string bindings, unknown context and constructor-input isolation. |
| Closed request surface | 5 | Caller bind, children, parent, promote and get_context operations are unsupported. |
| Current-context write | 4 | Exact task-a1 receipt and single-record storage delta; foreign-entry overwrite denial and unchanged store. |
| Write inheritance / no upward flow | 11 | New record appears only for task-a1 and work-a1; all ancestors, task-a2 and the employer branch remain unchanged. |
| Malformed tree rejection | 11 | Missing parent, self-parent, cycle, cycle behind a denied read boundary, duplicate ID, second root, no root, multiple parents, missing policy, invalid policy and empty tree. |
| Entry integrity | 2 | Unknown entry owner and duplicate entry ID reject construction. |
| Label independence | 11 | Relabel every node with the same arbitrary kind; all original sets remain exact. |
| Input order independence | 11 | Reverse node/entry input order; output remains identical. |
| Generic specialization | 12 | Add a level below work-a1; the new node inherits its chain, while all original contexts retain their original visibility. |
| Trusted read boundary | 3 | Stop inheritance at project-a, deny root direct retrieval and reject a caller's attempt to reopen the edge. |

No cache or content traversal API is implemented. Cache isolation and traversal
of graph-linked content are **deferred**, not counted as successful implementations.
The unsupported traversal request checks only establish the closed surface.
There is no promotion API, even in the correct fixture; ordinary writes cannot
perform it. No general security isolation or declassification claim follows.

## Mutation control

The runner-only `SiblingLeakControl` changes exactly one rule: it adds the current
context's siblings to the readable lineage. The same 221 oracle cases run in a
separate subprocess; expected values are unchanged.

Observed: **37 failures; subprocess exit 1**, as required. In particular,
`visibility/task-a1` unexpectedly contains `task-a2-memory`, and
`direct/task-a1/task-a2-memory` returns the forbidden record instead of denying it.
This detects the intended semantic defect, rather than merely detecting a crash.

The correct suite runs again after the isolated control and passes all 221 cases
with identical records. Evaluator/fixture/runner/verifier hashes remain unchanged.
No mutation is installed into `evaluator.py`; the faulty variant exists only in
the acceptance runner and is never the default. The standalone mutant command
below intentionally returns failure and must not be treated as an ordinary PASS.

## Findings, limitations and architecture implications

The **generic ContextNode/tree abstraction survives unchanged**. No class for Task
memory, Card memory or Project memory was necessary. Labels can be identical at
all levels. Ordinary downward inheritance does not require upward propagation,
nor does direct-ID retrieval require weakening isolation.

A useful edge finding is that **read policy must not hide invalid topology from
validation**. The constructor rejects a cycle even behind an inheritance stop.
The separate mutation demonstrates that ordinary-looking peer inclusion corrupts
both list and direct reads; both should share trusted lineage enforcement.

This is a finite executable proof over retained cases, not a formal proof for all
possible trees or production security. It intentionally does not establish:

- Authentication, transport confinement, multi-process/multi-tenant isolation or
  a sandbox against hostile code inside the trusted harness.
- Confidentiality of identifier existence, timing or metadata: write-ID collision
  errors are not designed as a privacy boundary.
- Per-entry classification, real security-domain boundaries, declassification,
  promotion, revocation or persisted policy-version semantics.
- Persistence, concurrency, deletion/reparenting, retries, durable waits/resumes,
  distributed lineage, provider adapters, cache safety or retrieval quality.
- A large-tree performance/resource-bound guarantee; constructor validation favors
  clarity over indexing and can revisit ancestor chains.

Source/fixture hashes support reproducibility, not tamper-proof evidence signatures.
Restate, PolicyGate, Completion Contracts, routing, Cognitive Loop, workers and
remote execution were unchanged. No dependencies were added and no model/backend
was used. Choosing a storage product remains unnecessary for this algebra.

Open questions: who issues production bindings; topology and policy revisions;
per-entry policy versus edge boundaries; resource budgets; revoked bindings;
idempotent writes and evidence/provenance envelopes. These belong to later bounded
contracts and experiments, not extensions hidden inside this evaluator.

## Exact proposed III.3 experiment — not started

Hypothesis: a runtime-issued ExecutionContext can expose a bounded memory capability
throughout one execution without callers choosing scopes or reinjecting all memory.

Use an **offline harness only** with the III.2 fixture and fake cognition, worker
and verifier callers. Pass the same trusted context reference through a proposed
experiment-only capability adapter. Run this fixed sequence:

1. Cognition reads at task-a1 and receives its four allowed literal entries.
2. Worker records one explicitly unverified observation at task-a1.
3. A later cognition call reads just in time and sees that new observation; no
   initial-prompt-only snapshot can satisfy this expected result.
4. Verifier reads through the same capability; the observation remains derived,
   unverified data and cannot assert Task completion or grant authority.
5. Another binding at task-a2 cannot see the new observation. Forged contexts,
   parent writes and direct-ID cross-scope reads are denied before returning data.
6. Exercise caller narrowing, a fixed 2 KiB UTF-8 response budget, and separate
   empty/denied/unavailable outcomes with deterministic fake-provider responses.

Retain the operation trace, exact request/response envelopes, entry IDs, byte counts,
denial reasons and source hashes. Compare an initial-only negative control that
misses the later observation. PASS requires exact expected results, enforced
budgets, unchanged bindings and explicit derived status; no production code,
database, real provider, model, Restate integration or actual Task completion.
This proposal does not settle durable propagation (III.10) or full security (III.4).

No human architectural decision is required to close III.2. **Explicit authorization
is required before III.3 begins.** No part of that adapter/ExecutionContext experiment
is implemented here.
